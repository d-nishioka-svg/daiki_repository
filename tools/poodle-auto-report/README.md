# POODLE 定例相談会 自動登録ツール（フェーズ1 MVP）

Googleカレンダーの「リスキリング定例相談会」予定をもとに、社内システム POODLE
(`https://poodle.race.co.jp`) の「定例相談会」実施報告を自動入力するツール。

> ⚠️ このディレクトリはレイスグループ社内の営業機密（POODLE・社内ポータルの
> 仕様）を含む可能性があります。社外と共有しないでください。

## 現在のステータス：スケルトンのみ・未実装

このツールはまだ**動作しません**。POODLEの「定例相談会」モーダルの実際のDOM構造
（要素セレクタ）が未確認のため、`src/poodleAutomation.ts` の要素操作部分は
プレースホルダーになっています。着手にあたり、下記「要確認事項」を実物を見ながら
一緒に詰める必要があります。

## スコープ（フェーズ1 MVP）

自動入力する項目:
- 日付
- 開始時刻／終了時刻
- 相談会実施状況 → 「実施済み」固定
- 対応トレーナー → 固定値（本人1名のみのため、プルダウンで固定選択）

自動化しない項目（フェーズ2以降）:
- 出席者（受講者ごとの出欠チェック）— 別途「受講者管理アプリ」との連携調査が必要
- 同席者（任意項目のため手動のままでよい）

## 確定した処理フロー（実画面確認済み）

当初は「案件一覧→企業名検索→契約詳細ページ→モーダル」という経路を想定していたが、
**実際の手作業フローはこうではなかった**。ユーザーは毎回、ダッシュボードの
「相談会(未報告)」タブを押して未報告の一覧から作業している。これに合わせて
自動化の設計も以下の通りに変更した。

1. `/home` にアクセスし、ダッシュボードの**「相談会(未報告)」タブ**をクリックする。
2. 表示される「定例相談会」の「未報告」テーブル（列: 状況／実施日／TSRコード／
   企業名／対応者／参加者）を取得する。
   - **要再確認**：実データで見えた行は「参加者」列に1名ずつ表示されていたため、
     POODLE側は「相談会1件＝受講者1名」の単位で未報告管理している可能性が高いと
     見ているが、**集団相談（1つのカレンダー予定に受講者が複数人）の実例で、
     本当に受講者の人数分だけ別々の行になるかはまだ確認できていない**
     （1行に複数名がまとまっている可能性も残っている）。ユーザーへの確認待ち。
3. （上記が「受講者ごとに別行」だった場合）カレンダー側の各イベントについて、
   **受講者（`attendeeNames`）1人ずつ**に対し、
   `企業名（完全一致） × 実施日（一致） × 参加者名（一致）` で該当する行を
   「未報告」テーブルから探す。
   - 見つかった行 → その行から編集画面/モーダルを開き、日付・開始・終了・
     対応トレーナー・相談会実施状況（実施済みに変更）を入力して保存する。
   - **見つからない行 → エラーではなく「スキップ」扱いにする**。対象イベントは
     過去に終了した相談会のみを対象にしている前提のため、「未報告」一覧に
     出てこない＝ほぼ「既に報告済みでこの一覧から消えた」と判断できる。これが
     そのまま重複登録防止の仕組みになる（当初考えていた、モーダルを開いて
     「相談会実施状況」ラジオの値を確認する、という余分な手順は不要になった）。
4. 案件一覧（企業名検索から契約詳細ページに入る経路）は、この設計では
   **不要**になった。`src/poodleAutomation.ts` の `navigateToCompanyDetail` は
   将来的に削除・置き換えの対象。

## 要確認事項（実装前に実物で確認する）

1. **カレンダー件名と企業名の突合 → 確認完了。企業名の完全一致検索で決定**
   - 件名パターン `✉️【定例相談会】{企業名} {担当者名}様`（集団相談の場合は
     `{企業名} {担当者名1}様, {担当者名2}様, ...`）を、実際のカレンダー予定
     （直近1ヶ月・全24件）で検証済み。全件このパターンに一致し、
     「先頭の空白区切りトークン＝企業名、残りはカンマ区切りの受講者名」という
     分割ロジックで企業名・受講者名とも正しく抽出できることを確認した
     （`src/googleCalendar.ts` の `parseConsultationEventTitle` に実装済み）。
   - 予定の `description` には `<a href="https://tsr.race.co.jp/pdf.php?id=NNN">
     企業情報</a>` というリンクが必ず埋め込まれているが、**実画面で確認した結果、
     このIDはtsr.race.co.jpページの内部ID（DB行番号的なもの）であり、POODLE側の
     TSRコードの値（例: 570514894）とは別物と判明した**。そのままではPOODLE側の
     検索キーとして使えないため、企業の突合には使用しない
     （`extractTsrPageId` として実装は残すが、参考情報にとどめる）。
   - 一方、**ダッシュボード「相談会(未報告)」一覧の「企業名」表記は、カレンダー
     件名から抽出した企業名と完全一致していることを確認した**（表記ゆれなし）。
     そのため、企業名の**完全一致**でのマッチングを基本方式として採用する。
     一致しない場合のみ `config/company-mapping.json` による手動マッピングに
     フォールバックする。
2. **POODLEログインとセッション再利用**
   - 社内GoogleアカウントのSSOログイン後の storage state (Cookie/セッション) を
     Playwright の `storageState` として保存し、以降のバッチ実行で再利用する方式で
     問題ないか。初回のみ手動ログインが必要。
3. **「相談会(未報告)」一覧・編集モーダルの実際のDOM構造 → フィールド構成は確認済み、
   セレクタ・遷移方法は未確認**
   - ダッシュボードのタブ構成（KOM(未設定)／KOM(未報告)／報告会(未設定)／
     報告会(未報告)／**相談会(未設定)**／**相談会(未報告)**）を確認済み。
     「相談会(未報告)」タブの一覧は列: 状況／実施日／TSRコード／企業名／
     対応者／参加者。
   - 「定例相談会」編集モーダル自体の入力項目は実画面で確認済み（上から）:
     企業名（表示のみ）／日付[必須]／開始・終了[必須]／出席者[必須]
     （氏名・テックタウンID・案件番号・契約期間・チェックボックスの一覧）／
     対応トレーナー[必須]（プルダウン）／同席者[任意]（プルダウン＋追加）／
     **相談会実施状況[必須]（ラジオ: 未実施／実施済み、デフォルト未実施）**／
     開催形式[必須]（ラジオ: Zoom／対面）・採番ID／ミーティングURL／ID／
     パスコード／備考[任意]／顧客の声[任意]／「次回予定」セクション
     （次回の日付/開始/終了/開催形式等、同じラベルが重複して存在）。
     フェーズ1で自動入力するのは 日付・開始・終了・対応トレーナー・
     相談会実施状況（実施済みに変更）のみ。他は手動のまま。
     日付/開始/終了は、Zoom発行時の情報がすでに入っている可能性があり
     （実物で確認したサンプルでは値が入った状態だった）、その場合は
     上書きせず一致確認のみで済む可能性がある（要確認）。
   - **未確認・残課題**：
     - ダッシュボードのタブ・一覧の実際のセレクタ（テーブル行の識別方法、
       クリックでモーダルが開くのか別画面遷移かなど）。
     - 「相談会(未報告)」一覧の各行から、どうすれば対応する編集モーダルを
       開けるか（企業名リンクか、行自体のクリックか、専用ボタンがあるか）。
     - Playwright codegen (`npx playwright codegen --save-storage=secrets/poodle-storage-state.json https://poodle.race.co.jp/home`)
       での記録が必要。
4. **重複登録防止の判定方法 → 解決**
   - 「相談会(未報告)」一覧に該当行が存在しない＝既に報告済みとして扱う
     （上記「確定した処理フロー」参照）。モーダルを開いて実施状況を確認する
     必要はなくなった。
5. **受講者管理アプリ（フェーズ2）**
   - 実体（Webアプリ／スプレッドシート／GAS等）、データ構造、API/エクスポート手段の
     ヒアリングが必要。

## セットアップ（予定）

```bash
cd tools/poodle-auto-report
npm install
npx playwright install chromium
cp .env.example .env   # 値を埋める。.env はコミットしないこと
```

### 環境変数（`.env`、コミット禁止）

| 変数名 | 内容 |
|---|---|
| `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` | Google Calendar API 用 OAuthクライアント（個人カレンダーのためサービスアカウントではなくOAuth） |
| `GOOGLE_OAUTH_REFRESH_TOKEN` | 初回認可後に取得したリフレッシュトークン |
| `GOOGLE_CALENDAR_ID` | 対象カレンダーID（通常は `primary`） |
| `POODLE_BASE_URL` | `https://poodle.race.co.jp` |
| `POODLE_STORAGE_STATE_PATH` | Playwright storageState の保存先（例: `./secrets/poodle-storage-state.json`、要 .gitignore） |
| `TRAINER_NAME` | 対応トレーナーとして選択する固定値（自分の氏名） |

初回のみ以下のような手動ログイン用スクリプトを別途用意し、Googleアカウントで
SSOログインした状態の storageState を保存する想定（未実装）。

```bash
npm run login   # ブラウザが開くので手動でGoogleログイン → storageState を保存
```

### 実行（ドライラン必須）

```bash
npm run report -- --dry-run   # 初回は必ずドライラン
npm run report                # 実際にPOODLEへ書き込む
```

ドライランでは、実際にPOODLEを操作する直前の「どの予定を／どの企業の／どの値で
登録しようとしているか」をコンソールとログファイルに出力し、書き込みは行わない。

## ログと機密情報の扱い

- ログ (`logs/`) には日時・対象企業名・登録した日付/時刻のみを記録し、受講者の
  個人情報や契約金額等の機密情報は書き込まない方針とする。
- `logs/` と `secrets/`（storageStateやトークンの保存先）は `.gitignore` 済み。
